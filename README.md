# Emerald Host — управляющий бот для Bothost

Исполнитель заданий из общей PostgreSQL и Telegram-бот с единственной командой `/start`. При добавлении проекта на [сайте](https://github.com/creepyside11/hostsait) исполнитель загружает код, устанавливает зависимости, запускает процесс, передаёт BOT_TOKEN и переменные, сохраняет статус и логи. Поддерживает остановку, запуск, перезапуск, GitHub-обновление и удаление.

## Установка на Bothost

1. Создайте PostgreSQL и задайте её адрес в `DATABASE_URL`. При запуске исполнитель автоматически создаёт недостающие таблицы из `sql/001_init.sql` перед восстановлением заданий и запуском Telegram. Повторный запуск сохраняет имеющиеся данные. Пользователю БД нужны права на создание таблиц в используемой схеме.
2. Создайте Telegram-бота в @BotFather. Его токен — **только для управляющего бота**, не используйте его же в дочерних ботах.
3. В Bothost подключите этот репозиторий, ветку `main`.
4. В дополнительных настройках включите **«Использовать собственный Dockerfile»**. Это описано в [документации Bothost](https://bothost.ru/docs/custom-dockerfile). Образ содержит Python, venv, pip, git и Node.js/npm. Docker внутри контейнера не требуется и не используется.
5. Заполните переменные ниже, подключите постоянное хранилище `/app/data` при наличии на тарифе. Команду запуска Dockerfile не переопределяйте. Публичный домен, webhook и входящий порт не нужны: все соединения исходящие.
6. Запустите **одну реплику**. Отправьте `/start` управляющему боту, затем добавьте простой проект через сайт и проверьте логи установки и запуска.

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | Прямое PostgreSQL-подключение или session pooler с TLS к той же БД, что у сайта; **не transaction pooler** |
| `ENCRYPTION_KEY` | Тот же 64-символьный HEX-ключ, что у сайта |
| `BOT_TOKEN` | Токен управляющего Telegram-бота |
| `SITE_URL` | Полный адрес сайта |
| `TRUSTED_CODE_ONLY` | `true`: явное включение режима для доверенного кода |
| `DATA_DIR` | По умолчанию `/app/data/emerald` |
| `MAX_RUNNING_BOTS` | По умолчанию `10`, уменьшите под RAM вашего тарифа |
| `INSTALL_TIMEOUT` | Лимит каждой команды установки в секундах, по умолчанию `600` |
| `MAX_WORKDIR_MB` | Периодически проверяемый размер каталога одного проекта, по умолчанию `1024` МБ |

`.env.example` — только справочник. В Bothost все значения задаются переменными окружения. Файл `.env` программа не загружает. Пользователь `emerald` запускает исполнителя и дочерние процессы; стартовый скрипт лишь создаёт и назначает владельца каталога данных после монтирования Bothost.

## Как запускается Python

1. Получить ZIP из БД или архив выбранной ветки публичного GitHub.
2. Безопасно проверить пути и размеры, распаковать, найти указанный файл запуска.
3. Создать отдельное виртуальное окружение `.venv`.
4. Если существует `requirements.txt` в корне проекта — выполнить `.venv/bin/python -m pip install --no-cache-dir -r requirements.txt`. Например, `aiogram>=3,<4` будет установлен здесь. Без файла зависимостей шаг пропускается.
5. Запустить `.venv/bin/python -u main.py` (или другой указанный `.py`) с пользовательскими переменными.
6. Писать stdout/stderr установки и бота в логи. Ошибка pip переводит проект в «Ошибка»; процесс бота при этом не запускается.

Для Node.js: `npm ci --omit=dev` с package-lock.json, иначе `npm install --omit=dev`, затем `node index.js` или указанный `.js` файл. Вложенный файл запуска поддерживается; cwd остаётся корнем проекта. Нативные Python-зависимости, которым нужны дополнительные системные библиотеки, могут потребовать изменения Dockerfile и пересборки исполнителя.

## Надёжность и ограничения

- Работает через очередь PostgreSQL, без попыток управлять чужими контейнерами через Bothost API.
- Обрабатывает одно действие одновременно. Установка не блокирует Telegram `/start` и heartbeat. Во время длительной установки следующая операция ждёт; отмена текущей установки через панель не поддерживается.
- Session advisory lock не допускает вторую реплику. При потере соединения с БД исполнитель завершает все известные процессы, чтобы не создавать дубли.
- После перезапуска контейнера незавершённые задания повторяются, боты с желаемым состоянием running запускаются снова. Если локальные файлы потеряны, исходники и зависимости восстанавливаются. Для GitHub берётся текущее содержимое ветки.
- Остановка убивает группу процесса, в том числе его дочерние процессы. Не используйте код, который демонизируется, создаёт новые сессии или пытается обойти управление процессами.
- Работает с polling-ботами; выделенные входящие порты и webhook URL для дочерних ботов не создаются.
- БД хранит зашифрованные настройки, ZIP и ограниченное количество логов каждого типа. Известные значения переменных и шаблоны Telegram-токенов скрываются; приложение бота всё равно не должно печатать секреты в преобразованном виде.
- **Это не песочница. Только ваши боты и код доверенных друзей.** Все процессы имеют одного пользователя ОС, доступ к общему файловому пространству и общим ресурсам. Код загрузки и установки зависимостей тоже исполняется с этими правами. Регистрация на сайте открыта; допускайте к исполнителю только доверенный код.
- Bothost определяет доступность запуска подпроцессов, диска, сети, RAM/CPU и фактическую страну сервера. Значение `nl` обозначает пул приложения, а не гарантирует физическую локацию. Проверяйте свой тариф. На один тариф нельзя обещать неограниченное количество ботов.
- Весь код/библиотеки исполнителя лежат в `/opt/emerald`, поскольку Bothost может монтировать исходники поверх `/app`.

## Локально

Нужны Linux, Python 3.11+, venv/pip, Node.js 22+ (для Node.js проектов), PostgreSQL. Установите зависимости исполнителя, экспортируйте переменные из таблицы и запустите `python main.py`. `DATA_DIR` укажите доступным для записи. Для автономных тестов Runner достаточно Python и cryptography: `python -m unittest discover -s tests -v`. Тест межъязыкового шифрования также требует соседний checkout `../hostsait` и Node.js.


## Если бот не отвечает и пишет UndefinedTable

Это ошибка отсутствующей таблицы в PostgreSQL: раньше исполнитель завершался на восстановлении заданий ещё до запуска Telegram polling. Теперь таблицы создаются автоматически.

На Bothost выполните **обновление исходников из main и пересборку Docker-образа** (обычный перезапуск старого контейнера не обновляет код). Ожидаемые строки: `PostgreSQL: таблицы Emerald Host готовы.` и `Emerald Host: исполнитель запущен, ожидаю задания.` После этого отправьте `/start`.

Если видите сообщение о правах PostgreSQL, предоставьте пользователю БД право CREATE в схеме и доступ к таблицам либо выполните `sql/001_init.sql` владельцем базы вручную. Адреса сайта и исполнителя могут отличаться pooled/direct endpoint, но должны указывать на одну базу и схему. Автосоздание таблиц не исправляет неверный адрес БД. Секреты в логи не выводятся.

## Обновление 1.1: логи, главный файл и Dockerfile

Пересоберите контейнер из последнего `main`. Помимо базовой схемы теперь автоматически применяется `sql/002_features.sql`: тип логов, режим сборки проекта и признак доступности Docker. Миграция добавочная, существующие аккаунты и проекты сохраняются. Сайт тоже умеет применить эти дополнительные столбцы к существующей базе.

- Установка пакетов и сборка Docker маркируются `build`; вывод приложения и его остановка — `runtime`. БД хранит до 1000 строк каждого типа. Старые смешанные логи остаются runtime.
- При отсутствии `main.py` проверяется `bot.py`. Главный файл существующего бота меняется на сайте через «Настройки». Работающий бот получает задание на перезапуск, остановленный не запускается автоматически.
- Регистрация на сайте теперь без приглашения. Проверки владельца и лимиты сохранены. Системный режим всё ещё предназначен исключительно для доверенного кода.

### Собственный Dockerfile

Системный режим остаётся обычным процессом внутри Bothost. Для произвольного Dockerfile нужен **отдельный доступный Docker daemon**; исполнитель не запускает Docker-in-Docker и не использует внутренний API Bothost для создания чужих контейнеров.

Опциональные переменные на Bothost:

| Переменная | Назначение |
| --- | --- |
| `DOCKER_HOST` | Например `tcp://docker.example.com:2376`; без него Docker-режим выключен |
| `DOCKER_TLS_VERIFY` | `1` обязательно для сетевого подключения |
| `DOCKER_CERT_PATH` | Каталог клиентских TLS-сертификатов (`ca.pem`, `cert.pem`, `key.pem`), доступный исполнителю |
| `DOCKER_NAMESPACE` | Уникальное имя для этой установки, по умолчанию `emerald-host` |
| `DOCKER_BOT_MEMORY` | Лимит памяти контейнера, по умолчанию `256m` |

SDK автоматически загружается из `requirements.txt`. После успешного подключения к daemon исполнитель передаёт сайту `supports_docker=true`; в форме становится доступен «Свой Dockerfile». Пользователь указывает относительный путь, например `Dockerfile` или `docker/Bot.Dockerfile`. Содержимое файла берётся из загруженного проекта, а команда запуска — из его CMD/ENTRYPOINT. Поле главного файла в этом режиме не используется. `requirements.txt` устанавливается командами Dockerfile, поэтому добавьте соответствующий `RUN pip install -r requirements.txt` самостоятельно.

Build context передаётся серверу Docker; переменные бота передаются только при запуске контейнера, не как build args. Контейнеры не получают Docker socket, каталоги исполнителя, его DATABASE_URL и токен управления. Заданы 1 CPU, 128 процессов, лимит RAM, удаление capabilities, запрет повышения привилегий и ротация Docker-логов. Dockerfile не является гарантией безопасного публичного хостинга: для недоверенных пользователей нужна отдельная архитектура, сетевые политики и защита сборщика.

Перезапуск/обновление пересоздаёт контейнер. Persistent volumes для пользовательских контейнеров пока не создаются; используйте внешнюю БД. Образы помечаются идентификатором бота и удаляются при удалении проекта; автоматическое удаление build cache не выполняется. При перезапуске управляющего бота его известные Docker-контейнеры останавливаются перед восстановлением очереди. При сетевом разрыве остановку удалённого контейнера невозможно гарантировать до восстановления соединения — проверяйте Docker-сервер. Не используйте один namespace для разных установок.

Реальный Docker daemon не предоставлен в среде разработки: интеграция проверена тестами адаптера; сквозную сборку и запуск необходимо проверить на подключённом Docker-сервере. Для обычного Bothost без отдельного daemon выбирайте системный режим.
